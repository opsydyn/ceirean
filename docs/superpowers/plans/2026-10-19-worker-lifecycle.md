# Worker Lifecycle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Qualify the selected XState/Effect cohort and deliver an offline worker lifecycle tracer that cannot mistake interruption, replay or uncertain readback for safe execution or cleanup.

**Architecture:** One XState machine orchestrates each worker operation inside a controller-owned Effect service. An atomic journal owns committed intent and authority; actors invoke services after those barriers and reconstruct into reconciliation, never replaying a VM snapshot. Domain holds pure schema data and evidence checks, not a second lifecycle reducer.

## Review Focus

1. A duplicated operation ID with different immutable input must refuse, not reuse the first worker under a misleading identity: Tasks 3 and 5.
2. Cancellation between claim and dispatch, or a lost create response followed by zero matches, must not authorize new work or confirm cleanup: Tasks 3-5.
3. Mutating caller-owned records, reordered mount evidence or a staging path with `..` must not alter journal history or authorize destructive work: Tasks 2-3.
4. Deadline equality, numeric overflow, backward/stale observations and reconstruction after expiry must block without granting fresh time: Tasks 2, 4 and 6.
5. Concurrent shutdown/acquire and a late child error must not orphan an actor, hide a failure or run cleanup twice: Task 5.

### Shared Data Decisions

Use schema-derived readonly records/unions, existing `CandidateIdentity`, `RunLimits`, `Digest` and `NonNegativeSafeInteger`:

- `WorkerOperationId`, `WorkerIntentId`, `WorkerIssuerId`, `WorkerHostId`, `WorkerDaemonId`, `WorkerContainerId`: branded nonblank strings, same identifier validation as existing IDs.
- `WorkerOperation`: `{ operationId, identity: CandidateIdentity, purpose: 'Baseline' | 'Candidate' | 'Verification', hostId, daemonId, imageDigest, sourceDigest, policyDigest, configDigest, configuration, custody, limits: RunLimits }`.
- `configuration`: `{ mounts: readonly { source, target, readOnly }[], network: string, security: { user: string, droppedCapabilities: readonly string[], noNewPrivileges: boolean } }`. Require exact values; reject duplicate mount targets/capabilities. Compare unique mounts/capabilities as order-independent sets, all other fields exactly. Digests are trusted fixture values, not hashes computed by this slice.
- `custody`: `{ controllerRoot: string, stagingDirectory: string, containerSlot: string, retainedArtifacts: readonly string[] }`. The container slot is one declared disposable resource until an immutable container ID is bound. Staging must be a strict descendant of the absolute controller root. Reject dot segments, ambiguous separators, root equality and retained-artifact overlap; no normalization that widens custody. These are synthetic POSIX-path checks, not symlink/host containment proof.
- `WorkerObservation`: subject `{ operationId, identity, hostId, daemonId }`, `atMs`, and `resources` containing exact candidate container records `{ containerId, operationId, identity, imageDigest, sourceDigest, policyDigest, configDigest, configuration, running }`, plus `staging: 'Present' | 'Absent' | 'Unknown'`. This is controller readback, never worker testimony. Multiple matches remain ambiguous, including one apparently valid match plus a foreign match.
- `WorkerReadyReceipt`: operation/identity/host/daemon/container IDs, pinned digests/configuration and `observedAtMs`. Receipt time must be within operation lifetime, not in the future relative to the injected clock; older observations cannot replace newer evidence.
- `WorkerIntent`: `{ intentId, operationId, issuerId, kind: 'Create' | 'Start' | 'Stop' | 'Remove', resource: containerSlot | WorkerContainerId, claimedAtMs, outcome }`. Outcome union: `Claimed`, `Completed { observation }`, `Failed { reason }`, `Unknown { reason }`. Identity of one action is `(operationId, kind, resource)` as well as intentId: a different intentId cannot repeat a claimed action. Create uses the slot; subsequent mutations use the immutable ID.
- `WorkerCleanup`: `CleanupPending { requestedAtMs, deadlineMs } | CleanupUnknown { requestedAtMs, deadlineMs, reason } | CleanupConfirmed { requestedAtMs, deadlineMs, observedAtMs }`. Before any cleanup request the journal uses `Option.none()`, not a success-shaped placeholder.
- `WorkerRefusal`: tagged data with a code from `InvalidInput`, `NotFound`, `IdentityMismatch`, `ConflictingOperation`, `StaleObservation`, `InvalidTime`, `DeadlineExpired`, `NotCurrent`, `Cancelled`, `NoCustody`, `ReadinessMismatch`, `AmbiguousObservation`, `UnresolvedIntent`, `AlreadyClaimed`, `ShuttingDown`; include operationId only when decoded. No raw error strings from drivers.

Canonical fixture: reuse run `run-1`, attempt `attempt-1`, generation `3`, candidate digest `a*64`, contract `contract-1`/`c*64`; operation `worker-1`, issuer `controller-1`, host `host-1`, daemon `daemon-1`, purpose Candidate. Image/source/policy/config digests `d*64`/`e*64`/`f*64`/`b*64`; container `container-1`, slot `slot-1`. Controller root `/synthetic/leviathan`, staging `/synthetic/leviathan/worker-1`, retained artifact `/synthetic/evidence/worker-1.json`. Mount staging at `/workspace` readOnly false, network `synthetic-isolated`, user `1000:1000`, droppedCapabilities `['ALL']`, noNewPrivileges true. These are not production approvals.

Time/limits: createdAtMs `900`, execution deadline `1000`, spentMicros `17`, repairs `1`, initial revision `7`; eligible time `999`, expired time `1000`. Readiness-pending observation interval `10ms`, bounded by the remaining original execution time. Cleanup request at `1000`, window `100ms`, exclusive deadline `1100`; orderly shutdown drain `100ms` from its first request. Repeated requests preserve the earliest deadline. Reject missing/nonfinite/negative/unsafe/overflow times and backward evidence. Expired execution may still clean owned resources before its separate cleanup deadline.

### Journal And Service Protocol

Define in `worker-contracts.ts`; these are data protocols, not handwritten Effect types:

- `WorkerJournalSnapshot`: `{ revision, operation, createdAtMs, editTimeFloorMs, outcomeEvidenceFloorMs, authority: { identity: CandidateIdentity, cancelledAtMs: Option<number> }, intents, containerId: Option<WorkerContainerId>, readiness: Option<WorkerReadyReceipt>, executionAuthorizedAtMs: Option<number>, cleanup: Option<WorkerCleanup> }`. Both floors are required `NonNegativeSafeInteger` fields, initialized at `createdAtMs` (canonical 900), preserved through detachment/reconstruction, never defaulted for missing persisted data. Do not persist the machine phase as a second authority.
- Ordering floors: every accepted controller edit monotonically advances `editTimeFloorMs` to its `atMs`. Every accepted Completed/Failed/Unknown reply monotonically advances `outcomeEvidenceFloorMs` to its reply time; accepted readiness/cleanup observations also retain their evidence time. Claims atomically clear readiness. RecordReadiness and AuthorizeExecution require exact-bound post-action evidence at or beyond the latest claim and outcome/evidence floor, not an old retained receipt. Keep evidence time separate from administrative edit time: a late truthful reply/evidence may predate cancellation/admin edits, but its current edit cannot move backward. Same-run cancellation checks every affected record's ordering before atomic fan-out; fan-out preserves both floors and includes supplied edit/cancellation time. Timestamp-free authority controls retain existing floors rather than invent a clock. Replacement does not reset floors; later same-run registration inherits existing floors and refuses backward registration time. No domain outcome-shape change or hidden timestamp cache.
- `WorkerJournalEdit`: discriminated requests `Register { operation, createdAtMs }`, `Claim { intent }`, `RecordOutcome { reply: WorkerMutationReply }`, `RecordReadiness { receipt }`, `AuthorizeExecution`, `RequestCancellation { cleanupWindowMs }`, `RequestCleanup { cleanupWindowMs }`, `RecordCleanup { observation: WorkerObservation }`. Every request carries operationId and controller-clock atMs; all except initial Register carry expectedRevision. Register expects absence. Claim is authorized atomically against the stored authority and custody: Create/Start require current uncancelled authority and execution time; Stop/Remove require the operation's own custody and cleanup time, not current generation. AuthorizeExecution requires matching current readiness, no cancellation, unexpired execution time and no existing execution authorization; reconstruction never invokes an already-authorized task again. RecordCleanup derives confirmed versus unknown evidence from the validated observation and unresolved intents, not a caller-supplied confirmation flag. Only controller-owned test controls may replace authority to simulate RunCoordinator.
- `WorkerJournalResult`: `Committed { snapshot } | Conflict { operationId } | Refused { refusal }`. Revision exhaustion is tagged operational failure. Existing or different-issuer claims cannot be reissued, even under a fresh expectedRevision; a claim records the sole issuer. Recording another issuer's outcome refuses. Unknown/Claimed create or start can only resolve with authoritative synthetic evidence, not a zero-match guess.
- `WorkerJournalDriver`: synchronous `load(operationId) -> Result<Option<WorkerJournalSnapshot>, WorkerJournalError>` and `commit(edit) -> Result<WorkerJournalResult, WorkerJournalError>`. Driver owns the full atomic authority/claim/custody check; no callbacks holding a lock across an Effect. Current identity/cancellation is shared by every operation for the same run: replacement/cancellation atomically fences all same-run snapshots and revisions. Reject incoherent same-run seed authority. Superseded operations cannot cancel replacement authority; their own bounded cleanup remains allowed.
- `WorkerMutationRequest`: `{ operation, intent }`; `WorkerMutationReply`: `{ operationId, identity, hostId, daemonId, intentId, issuerId, atMs, outcome }`, where outcome is the WorkerIntent outcome union excluding Claimed. Generic decoding permits zero or one container in an explicit Completed envelope, rejects ambiguity, and checks subject/time consistency; this accepts representation, not action authorization. The journal must validate against its stored intent, issuer, operation/host/daemon, bound immutable resource ID and relevant times: Create/Start require matching presence, Stop requires matching stopped presence, and Remove requires authoritative direct-ID absence. No-match observation alone is never a mutation-completion reply and cannot resolve Unknown/Claimed Create/Start; only the appropriately bound Remove completion may resolve from exact-ID absence. Unknown records uncertainty. Runtime-decode replies and verify subject/issuer/time before recording; add pure `decodeWorkerMutationReply(input: unknown) -> Result<WorkerMutationReply, WorkerRefusal>` in Task 2.
- `WorkerExecutionRequest`: `{ operation, readiness, authorizedAtMs }`; `WorkerExecutionReply`: `{ operationId, identity, completedAtMs }`. This synthetic result is not a qualification receipt; validate its subject/time, and never call qualifyRun from this lifecycle. Its completion requests cleanup. Runtime-decode this reply in the engine task using its schema.
- `WorkerObservationRequest`: `{ operation: WorkerOperation, containerId: Option<WorkerContainerId> }`. Some directs readback of the bound immutable ID on its host/daemon even when discovery labels differ; None requests unbound discovery. A fresh service needs no identity cache. Discovery absence never resolves outstanding Create/Start uncertainty.
- `WorkerMechanismDriver`: native functions `mutate(request: WorkerMutationRequest, signal: AbortSignal) -> Promise<Result<unknown, WorkerMechanismError>>`, `observe(request: WorkerObservationRequest, signal: AbortSignal) -> Promise<Result<unknown, WorkerMechanismError>>`, `execute(request: WorkerExecutionRequest, signal: AbortSignal) -> Promise<Result<unknown, WorkerMechanismError>>`. This execute is a synthetic task, not approved shell/model execution. Replies must decode and match the current intent/operation before journal advancement.
- Real `makeWorkerJournal(driver)` and `makeWorkerMechanism(driver)` defer invocation, flatten Result, map native throws/rejections and add named spans, following existing factories. Their outputs infer `WorkerJournal` and `WorkerMechanism` Context.Service shapes via `ReturnType`. Effect-native fakes implement `.of` directly, never bounce through runtime execution/Promises.
- Errors are Data.TaggedError: `WorkerJournalError { operation: 'load' | 'commit', code: 'ReadFailed' | 'CommitFailed' | 'InvalidData' | 'RevisionExhausted' }`, `WorkerMechanismError { operation: 'mutate' | 'observe' | 'execute', code: 'Unavailable' | 'InvalidReply' }`, `WorkerLifecycleRuntimeError { operationId, code: 'ActorFailed' | 'ObservationFailed' | 'DrainExpired' }`. Include no raw underlying message/cause in public output. Expected refusals remain values; typed service failures stay visible.

The claim is the linearization point for permission, not an external transaction. A cancellation committed before claim prevents dispatch. If cancellation wins after claim, a final journal read prevents dispatch when observed; once work is dispatched it may finish externally and stays unresolved until reconciled. Do not claim a physical cancellation fence between journal read and external acceptance. Cleanup cannot confirm while a create/start might still materialize a resource.
